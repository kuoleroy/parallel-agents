# 并行 AI 协作开发方法论

> 完整长文版。想快速上手看 [README](../README.md)，想让 AI 直接执行看 [SKILL.md](../SKILL.md)。

> **一句话**：主控定契约、排波次、管合并；多个执行 AI 各占一个 worktree 与独占文件边界并行推进。
> 目标不是「用上并行」，是**单位时间产出更多、返工更少**。

本文件与具体工具无关——Claude Code、Trae、Cursor、Codex、OpenCode、Antigravity 等任何能读写文件、跑 git/shell 的 AI 都适用。

---

## 设计原则（速度与质量怎么取舍）

1. **一切为减少返工服务**。返工是并行开发最大的时间黑洞——一次「接口形状理解不一致」，能让两个分支白干半天。宁可前置多花 30 分钟定契约，也不要合并时返工 4 小时。
2. **协调开销必须小于并行收益**。超过 5~6 个执行窗口，主控的合并与对齐成本会吃掉全部增益。
3. **每个交接点都在丢上下文**。所以角色按项目规模伸缩，**不搞固定编制**。加角色是成本，不是能力。
4. **验收必须能跑出结果**。「看起来对」不算完成。

---

## 0. 何时用 / 何时不用

**适合**：项目级建设，且能拆成若干**文件不重叠、可独立验收**的模块（如：后台数据层 / 部署编排 / 数据导入 / 前端详情页 / 搜索）。

**不适合**：
- 小改动（一个 bug、一个函数）——协调开销大于收益，直接单窗口做。
- 任务之间**共享大量文件**——并行会天天冲突，此时要么串行，要么先把契约拆得更细（把共享部分冻结，改由主控统一维护）。
- 需求还没定清楚——**先写文档、定方向，再开分支**。
- **任务数 < 3**——两个任务并行，收益基本被主控的协调成本抵消，不如串行做完。

判断口诀：**「这些任务，各自的文件清单能不能做到互不相交？任务数够不够 3 个？」** 都满足就并行；不满足先重构边界。

## 1. 角色：按规模伸缩，不是固定编制

| 档位 | 编制 | 适用场景 | 典型任务数 |
|---|---|---|---|
| **L1 轻量** | 主控 ×1 + 执行 ×2~3 | 功能模块、页面、数据层；架构已明确 | 3~6 |
| **L2 标准** | 主控 ×1 + 架构 ×1 + 执行 ×3~4 + 验收 ×1 | 新项目从 0 起；跨端项目；多接口协作 | 6~15 |
| **L3 完整** | L2 + 安全审查 ×1 + 文档 ×1 | 对外发布、涉钱涉权限、需要交付文档 | 15+ |

**默认从 L1 起。** 只有当「契约没人定」或「没人独立验收」确实造成问题时，才升档。

**关键设计**：架构角色**只在 S0 出现一次**（定契约），定完就退场，不参与日常。验收角色**只在 S3 出现**。这就是它不会拖慢速度的原因——GH 那套的问题是让 14 个角色全程在线、逐段交接。

### 主控（协调，不做实现）
- 维护**项目知识文档**（方向、架构、数据模型、决策、坑）——唯一事实来源。
- **S0 定契约**（或派架构角色定，自己拍板）。
- **排波次**、写任务书、登记「分支 ↔ worktree ↔ 独占文件」归属表。
- **冻结共享文件**，统一预装依赖。
- **收口**：对每个分支跑**合并前闸门**（边界 → 构建 → 实测 → 回归），全绿才 `merge --no-ff`，最后清理。
- 等待交付时就真的等，不插手执行 AI 的工作区。

### 架构角色（L2+，只在 S0）
- 产出**接口契约、数据模型、共享类型**三件套，落 `docs/contracts/`。
- 定完 commit 到 main 即退场。**不写业务代码，不参与日常答疑**（答疑走文档）。

### 执行 AI（干活，守边界）
- 只改任务书里「独占文件」列出的文件；不碰「不要动」清单。
- 不动共享文件、不装依赖、不起数据库/容器、不占端口、不改别人的 worktree。
- 完工产出**交付契约**：改了什么、怎么验证的、还有什么隐患、下游要知道什么。

### 验收角色（L2+，只在 S3）
- 在主控合并后的干净栈上跑验收清单。
- **只做判定，不做修复**——红了退回主控，由主控重开任务书。

## 2. 核心模型

```
                    ┌──────────────────────────────────────┐
                    │  主控 (integrator / owner)            │
                    │  · 唯一事实来源：项目文档 + 契约       │
                    │  · 排波次、写任务书、冻结共享文件      │
                    │  · 统一预装依赖                        │
                    │  · 体检 → 合并 → 端到端验收            │
                    └──────────────┬───────────────────────┘
                                   │  按波次放行
     ┌─────────────────────────────┼─────────────────────────────┐
     ▼                             ▼                             ▼
  波次 1                        波次 2                        波次 3
  无依赖，全并行                 依赖波次1契约                  集成收口
  worktree A / B / C            worktree D / E                worktree F
  执行 AI 1 / 2 / 3              执行 AI 4 / 5                  验收 AI
```

- **主控**：可以是一个人，也可以是一个专门的主控 AI 窗口。
- **执行 AI**：**一个任务 = 一个窗口 = 一个分支 = 一个 worktree**，逐一对应，不混岗。
- 所有分支从同一个 `main` 起，最终都并回 `main`，**只有主控动 `main`**。仓库用 `master` 也一样，下文命令里的 `<base>` 指主干分支；脚本会自动探测 `main`/`master`。

## 3. 四段流程

### S0 · 契约冻结（唯一必须串行的阶段）

**开分支前必须冻结三样**，落在 `docs/contracts/`：

1. **接口契约**：端点、方法、请求/响应 schema、错误码
2. **数据模型**：表/集合、字段名、类型、可空性、索引
3. **共享类型**：前端 TS 类型 / 后端 DTO，放在共享文件里

冻结 = commit 到 `main`，此后**任何分支不得修改**。

**为什么这一步最值钱**：并行开发的返工，绝大多数来自「两个 agent 对同一个字段名 / 接口形状理解不同」。契约冻结把这类返工从「合并时发现」提前到「开工前消除」——**这是唯一一个花时间反而省时间的环节**。

契约文档最小形态（一个文件就够）：

```markdown
# 契约 v1（冻结于 <commit sha>）

## 接口
GET /api/items?q=&page=  →  { items: Item[], total: number }
  错误: 400 INVALID_QUERY | 404 NOT_FOUND | 500 UPSTREAM_DOWN
POST /api/items         ←  { title: string }  →  { id: string }

## 数据模型
items(id text pk, title text not null, created_at timestamptz default now())
idx_items_created_at (created_at desc)

## 共享类型
type Item = { id: string; title: string; createdAt: string }
```

**改契约的规矩**：只有主控能改；改了必须广播 + 所有在跑的分支 `git merge <base>` 对齐（base 是 `main` 或 `master`，脚本会自动探测，也可用 `BASE_BRANCH` 指定）。改契约不是禁忌，但要留痕、要同步。

### S1 · 拆解与任务书

- 把需求拆到「文件不重叠 + 可独立验收」。
- 按依赖排波次（见 §4）。
- 每任务用 `scripts/new-task.sh` 建分支 + worktree + 任务书，并**自动登记归属表**：

  ```bash
  scripts/new-task.sh 01 data src/db migrations
  ```

  归属表落在 `docs/tasks/ownership.md`，是**机器可读**的（`gate.sh` 靠它拦越界）：

  ```markdown
  | 任务 | 分支 | worktree | 波次 | 端口 | 独占文件 | 状态 |
  |---|---|---|---|---|---|---|
  | 01 data | feature/data | ../wk-data | 1 | 3101 | src/db migrations | active |
  | 02 search | feature/search | ../wk-search | 2 | 3102 | src/api/search.ts | active |
  ```

  列顺序不能改；状态取 `active / merged / abandoned`。波次需要人工补，其余由脚本填。
  端口按 `BASE_PORT + 任务号` 分配，冲突自动顺延——闸门要起服务，必须一人一口。

- **建任务即校验边界**：清单与在跑任务重叠、或命中冻结文件，`new-task.sh` 直接拒绝开工并打印冲突对。边界不是约定，是硬拦。
- 冻结清单落在 `docs/tasks/frozen.patterns`（一行一个通配），首次运行自动生成，按项目改它并 commit。
- 每个 worktree **预装依赖**。

### S2 · 并行执行

- 同一波次内全并行，**波次之间串行**。
- 执行 AI 只读：项目文档 + 契约 + 自己的任务书。
- 完工产出交付契约（见 §7 末）。

### S3 · 收口与验收

按 §8 合并闸门执行。合并完成后，让其余 worktree `git merge <base>` 快进对齐，**再开下一波**。

### S4 · 回流（红了怎么办）

| 验收结果 | 动作 |
|---|---|
| 全绿 | 收工，更新文档与归属表 |
| 单个任务红 | **重开该任务书**（不修旧分支，开新窗口新分支），主控不亲自补代码 |
| 契约本身有缺陷 | 回 S0 改契约 → 广播 → 所有波次重排 |
| 多个任务都红在同一处 | 说明契约漏了东西，回 S0，不是执行 AI 的问题 |

**关键**：不要在原分支上打补丁。旧窗口带着旧假设，补丁会引入隐性冲突——**新任务开新窗口**。

## 4. 波次编排（真正的提速点）

这一节最容易被忽略，收益最大。

**错误做法**：把所有任务同时开出去 → 然后卡在冲突和等待上，主控变成人肉串行器。
**正确做法**：按依赖分波，波内并行，波间串行。

```
波次 1（无依赖，全并行）: 数据模型 / 路由骨架 / 设计令牌 / 部署编排
波次 2（依赖波次1契约）: 后端接口 / 前端页面 / 数据导入
波次 3（依赖波次2）:     集成联调 / 端到端验收
```

**判断依赖的标准**：**A 的产出是否出现在 B 的输入里**（接口形状、字段名、类型定义、表结构）。

- 是 → 真依赖，B 放后一波。
- 只是「逻辑上相关」「以后可能会用到」→ **不算依赖，放同一波**。

这条判断标准能砍掉大量假依赖——很多人把「相关的都串起来」，白白浪费并行窗口。

**波次规划要点**：
- 波次 1 尽量塞满（这是唯一能真正全速跑的窗口，因为没有任何上游等待）。
- 单波内任务数 ≤ 5（超过主控合并不过来）。
- 每波结束：合并 → 其余 worktree 对齐主干 → 再开下一波。**不要在波次中途合并**。

## 5. 铁律（九条）

1. **一个任务 = 一个分支 = 一个 worktree = 一条独占文件边界**
   用 `git worktree` 共享同一个 `.git`，不必复制仓库；每棵工作树独立装依赖。

   ```bash
   git worktree add ../wk-taskA -b feature/taskA <base>
   git worktree list
   ```

   实际用 `scripts/new-task.sh` 建，它会顺手校验边界、分配端口、登记归属表。

2. **契约先行**：接口、数据模型、共享类型冻结在 `docs/contracts/`，改只能主控改且必须广播。**没有契约不开分支。**

3. **冻结共享文件**：锁文件（`pnpm-lock.yaml` 等）、共享类型、迁移、主文档、compose，任何分支不许改，只由主控统一维护。清单落在 `docs/tasks/frozen.patterns`，`new-task.sh`（建任务时）和 `gate.sh`（收口时）都会读它。锁文件**只能由 install 自动生成**，绝不手改。

4. **依赖由主控预装**：执行 AI 不许 `pnpm install` / `pip install` / 起 docker / 监听端口。避免并发抢端口、避免依赖漂移。

5. **任务书即契约**：动工前先拿到任务书（见 §7）。没有任务书不动手。

6. **文档为唯一事实来源**：方向、数据模型、接口信封、字段约定、已知坑，全部落文档；AI 之间靠文档对齐，不靠口头上下文。

7. **按波次放行**：波内并行、波间串行。不要一次把所有任务开出去。

8. **合并闸门在合并之前**：边界 → 构建 → 起服务实测 → 回归，全绿才 `git merge --no-ff`（见 §8）。**`SKIP` 不等于通过**——`REQUIRE_FULL=1` 下任何跳过都算红。

9. **没进归属表不许合并**：`docs/tasks/ownership.md` 里查不到分支，闸门直接拒。

## 6. 冻结清单（开分支前逐项打勾）

```markdown
## 共享文件冻结清单
- [ ] 锁文件（pnpm-lock.yaml / package-lock.json / poetry.lock）
- [ ] 共享类型（src/types/**、shared/**）
- [ ] 数据模型 / 迁移目录（migrations/**）—— 只主控写
- [ ] 骨架数据 / 种子数据
- [ ] 主文档（README、docs/**、docs/contracts/**）
- [ ] 编排文件（docker-compose.yml、Dockerfile、CI 配置）
- [ ] 环境变量样例（.env.example）
```

前 6 项是人工核对；真正的强制力在 `docs/tasks/frozen.patterns`——一行一个通配，脚本逐文件比对。人工清单负责「别忘」，模式文件负责「拦下」。

## 7. 任务书模板（固定七段）

`scripts/new-task.sh` 生成的骨架就是下面这个形状——分支、worktree、契约 sha、独占文件、端口、「不要动」清单都自动填好，人只补目标、前置、步骤、验收标准。

```markdown
# 任务书 NN · <任务名>

- 分支：feature/<name>
- worktree：<绝对路径>
- 波次：<1 / 2 / 3>
- 前置：<依赖哪些任务/契约，或"无硬依赖">
- 上游契约：docs/contracts/ @ <commit sha>
- 分配端口：<本任务专用端口，起服务只用它>

## 目标
一句话说清"做完之后能多什么能力"。

## 独占文件
- <只列本任务可改的文件/目录，尽量收窄；脚本据此拦越界>

## 不要动
- <冻结文件（脚本自动生成）+ 其他任务的 worktree 与独占文件>

## 步骤
> 环境：依赖已由主控预装；不要自己起服务、不要抢端口。
1. …（分步，含关键接口/字段约定）
2. …

## 验收标准
- <可机器验证的硬指标：命令 + 期望结果>
- <"既有行为零改动"之类的回归要求>

## 注意
- 新增依赖必须成熟且许可宽松（MIT/Apache-2.0）；能不新增就不新增
- 验收由主控/验收 AI 在干净栈执行
- 完工必须产出交付契约（见下）
```

### 交付契约（执行 AI 完工时产出）

```markdown
## 交付契约 · 任务 NN
- 改动文件：<列表，应完全落在"独占文件"内>
- 自测命令与结果：<命令 → 实际输出>
- 对契约的实现情况：<逐条对照上游契约，有无偏差>
- 遗留隐患：<没做的、妥协的、边界未覆盖的>
- 下游须知：<新引入的字段/行为/副作用>
```

**任务书写作要点**：
- 独占文件清单是**边界**，宁可窄不可宽。
- 验收标准必须**能跑出结果**（命令 + 期望输出），不写「做得好一点」。
- 「上游契约」必须带 commit sha——否则执行 AI 可能对着旧契约干活。

## 8. 合并闸门（主控收口）

**闸门跑在合并之前**，对象是这个分支自己的 worktree。理由很直接：合并完再发现问题，脏的是主干；合并前发现，脏的只是那条分支。

对每个完工分支按顺序做，**任一步红就退回，不往下跑**：

| # | 步骤 | 谁做 | 红意味着什么 |
|---|---|---|---|
| 1 | 前置：基线分支探测 + 分支必须在归属表里登记 | 自动 | 没走流程的分支，直接拒 |
| 2 | 体检：worktree 是否还有未提交改动、有无验证残留（`*.verify.*`、临时 `Dockerfile`） | 自动 | 交付物不完整 / 有垃圾 |
| 3 | **边界**：每个改动文件必须落在自己的独占清单内，不得命中冻结文件，不得踩到别的在跑任务 | 自动 | 方法的核心承诺，越界即退回 |
| 4 | 任务书「不要动」复核 | 自动 | 显式保护区被改了 |
| 5 | 构建：`BUILD_CMD`（compose config、前端 build 等） | 自动 | 编译不过 |
| 6 | 接口实测：闸门自己用**分配端口**起服务 → 探健康端点 → 跑边界用例（非法参数必须 4xx）→ 收掉 | 自动 | 契约写了但没实现 |
| 7 | 回归：`TEST_CMD` + 改动文件清单（既有代码是"改"还是"新增"） | 自动 | 既有行为被动到 |
| 8 | 安全检查（密钥硬编码、未校验输入、越权、SQL 拼接、日志泄露 PII）、清理残留 | **人工** | 脚本不代答 |
| 9 | `git merge --no-ff <branch>`；冲突**主控亲自解**，不退回给执行 AI | 人工 | — |

第 6 步解决了方法里的一处矛盾：执行 AI 不许起服务、不许抢端口，但接口实测又需要一个在跑的服务。答案是——由闸门在**该任务专属端口**上起、探完立刻收，执行 AI 全程不动服务。

`scripts/gate.sh` 覆盖 1~7：

```bash
BUILD_CMD='pnpm -w build' \
TEST_CMD='pnpm -w test' \
SERVE_CMD='node server.mjs' \
  scripts/gate.sh feature/search
```

输出是一行一结果的计数报告，结尾 `OK / SKIP / FAIL` 三个数。**没配的步骤报 `SKIP`，不会假装通过**；CI 里加 `REQUIRE_FULL=1`，任何 `SKIP` 直接算红——配置不全的闸门比没有闸门更危险，因为它看着像绿了。

跑完 `bash tests/run-test.sh` 可以复现这套拦截（零成本，纯 bash/git/node，不消耗任何 token）；实测结果与真实输出实录在 [evidence.md](evidence.md)。

> 合并到主干后，让其余 worktree `git merge <base>` 快进对齐，避免长期分叉。

把闸门自动化，是第二个「花时间省时间」的投入——手点 checklist 每次 15 分钟，脚本 40 秒；而且脚本不会因为「看起来对」就放行。

## 9. 验收标准怎么写

好的验收标准长这样（**命令 + 期望输出**）：

```markdown
- [ ] `pnpm build` 退出码 0，无 TS error
- [ ] `curl -s localhost:3000/api/items?q=abc` 返回 200，且 `jq '.total'` 为数字
- [ ] `curl -s "localhost:3000/api/items?page=abc"` 返回 400，body 含 `INVALID_QUERY`
- [ ] 关掉上游服务后，同端点返回 503，body 含 `UPSTREAM_DOWN`（降级不崩）
- [ ] `git diff <base> -- src/db/` 为空（既有数据层零改动）
```

坏的验收标准（**不要写**）：

- ❌「功能正常」
- ❌「代码质量良好」
- ❌「性能达标」（没说阈值）
- ❌「参考现有实现」（现有实现可能也是错的）

---

## 10. 反模式（别做）

- ❌ **一个窗口跑多个任务** → 上下文混淆、越界改动。
- ❌ **复用旧窗口做新任务** → 旧任务的工作假设残留，引入隐性冲突；**新任务开新窗口**。
- ❌ **跳过契约直接写码** → 返工成本远超省下的时间，这是并行开发最大的坑。
- ❌ **把「相关」当「依赖」** → 假依赖把并行窗口浪费成串行。
- ❌ **一次把所有任务全开出去** → 主控变人肉串行器，还天天解冲突。
- ❌ **执行 AI 自己装依赖 / 起库 / 抢端口** → 并发事故。
- ❌ **手改锁文件 / 共享类型** → 合并冲突重灾区。
- ❌ **没有可机器验证的验收就宣布完成**。
- ❌ **主控下场写业务代码** → 没人管收口。
- ❌ **任务之间文件重叠还硬并行**。
- ❌ **在原分支上打补丁修验收失败** → 开新分支。
- ❌ **为了「流程完整」上 14 个角色** → 每个交接都在丢上下文，速度崩。
- ❌ **边界只写在文档里，不落到脚本** → 文档管不住手，越界要等到合并时才发现。
- ❌ **把 `SKIP` 当通过** → 配置不全的闸门会一路放行到合并，比没闸门更危险。

---

## 11. 真提速 vs 假提速

| 看起来提速 | 实际效果 |
|---|---|
| 多加几个执行窗口 | ❌ 超过 5~6 个，主控合并成本吃掉全部收益 |
| 跳过契约，直接开写 | ❌ 返工成本 = 省下时间的 3~5 倍 |
| 一次全开，看起来最并行 | ❌ 冲突排队，实际比串行还慢 |
| 让 AI 自己装依赖，省主控的事 | ❌ 并发抢端口 / 依赖漂移，调试时间远超装依赖时间 |
| **先定契约再开分支** | ✅ 消除最大一类返工 |
| **正确分波次，波 1 塞满** | ✅ 唯一能全速跑的窗口不浪费 |
| **依赖主控预装** | ✅ 每个执行 AI 省 2~3 分钟起步，且不冲突 |
| **任务书自包含 + 带契约 sha** | ✅ 执行 AI 不用探索代码库、不用提问 |
| **闸门脚本化** | ✅ 每次收口从 15 分钟降到 40 秒 |
| **文件边界收窄** | ✅ 合并几乎零冲突 |

## 13. 机器层（本仓库提供的部分）

方法论里能被机器执行的部分，都固化成了脚本。这是它和「一篇讲并行开发的文章」的区别。

| 文件 | 作用 |
|---|---|
| `scripts/new-task.sh` | 一条命令建分支 + worktree + 任务书 + 归属表登记 + 端口分配；**边界重叠或命中冻结文件直接拒绝开工** |
| `scripts/gate.sh` | 合并前闸门，自动跑 §8 的 1~7 步，任一步红即非零退出 |
| `scripts/parallel-lib.sh` | 两个脚本共用的边界语义（归属表解析、通配匹配、重叠判定、基线探测） |
| `docs/tasks/ownership.md` | 归属表，`任务 \| 分支 \| worktree \| 波次 \| 端口 \| 独占文件 \| 状态`，脚本读写 |
| `docs/tasks/frozen.patterns` | 冻结文件通配清单，一行一个 |
| `docs/evidence.md` | 实测拦截记录与真实输出 |
| `tests/run-test.sh` | 零 token 端到端复现：往流程里注入 8 种违规，逐条断言被拦下 |
| `AGENTS.md` | 给只认规则文件、不装 skill 的 agent 的精简可执行版 |

诚实的边界：这套脚本验证的是**机制**（违规会被拦下），不是**效果**（多 agent 并行真的更快）。后者要在真实项目上跑对照实验，本仓库没有那个数据，也不假装有过。
